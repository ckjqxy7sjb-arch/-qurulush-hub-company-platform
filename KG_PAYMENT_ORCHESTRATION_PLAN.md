# Kyrgyzstan payment orchestration plan

Дата: 14.09.2026

Этот документ фиксирует платежный контур Qurulush Hub для госпошлин, начислений, штрафов и иных платежей строительной компании. Цель - дать кнопку оплаты из карточки уведомления, но закрывать платеж только после явного подтверждения уполномоченного пользователя и сверки ответа провайдера.

## Источники для сверки провайдеров

- НБКР: реестр операторов платежных систем и платежных организаций - https://www.nbkr.kg/index1.jsp?item=97&lang=RUS
- НБКР: реестр операторов взаимодействия - https://www.nbkr.kg/index1.jsp?item=3488&lang=RUS
- НБКР: нормативные документы по платежным системам - https://www.nbkr.kg/contout.jsp?item=106&lang=RUS
- Элкарт / Межбанковский процессинговый центр - https://elcart.kg/
- Пример wallet/business канала: MegaPay - https://megapay.kg/

Перед production список провайдеров нужно обновить по действующим реестрам НБКР и договорам банка/платежной организации. Нельзя считать демо-каталог полным юридическим источником.

## Каналы оплаты

- Банковский счет компании и интернет-банкинг.
- Элкарт и банк-эквайринг через МПЦ или банк-партнер.
- QR/deeplink в мобильный банк или электронный кошелек.
- Платежная организация/агрегатор из актуального реестра НБКР.
- Ручная бухгалтерская отметка с квитанцией, если callback провайдера недоступен.

## Процесс оплаты

1. Платформа получает уведомление о госпошлине, штрафе или начислении.
2. Создается payment intent: объект, основание, сумма, срок, ответственный, provider route.
3. Бухгалтер или генеральный директор нажимает `Оплатить` и выбирает канал оплаты.
4. Provider возвращает payment id, статус, redirect/deeplink или квитанцию.
5. Callback/reconciliation сверяет сумму, назначение, валюту, статус и external id.
6. Платформа переводит платеж в `Оплачено` только после подтверждения provider callback или ручной бухгалтерской сверки.
7. Квитанция, payment id и audit event сохраняются в карточку объекта/штрафа/госпошлины.

## Контроли безопасности

- Нет автоматического списания без явного подтверждения пользователя с правом платежа.
- Секреты провайдера хранятся только в server env/secret storage, не во frontend и не в launch bundle.
- Любой спорный штраф можно отправить в обжалование вместо оплаты.
- Audit должен хранить actor, role, object id, amount, provider, payment id, status и timestamp.
- Повторная callback-нотификация должна быть идемпотентной, чтобы не задвоить платеж.

## Следующие работы

1. Выбрать банк или платежного агрегатора и получить merchant/API договор.
2. Сверить полный список актуальных провайдеров по реестрам НБКР на дату подключения.
3. Реализовать provider registry, invoice API, redirect/deeplink, callback и reconciliation job.
4. Пройти тестовую оплату на sandbox/prod-test контуре и сохранить evidence.
