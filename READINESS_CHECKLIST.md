# Readiness checklist

## Уже подтверждено тестами

- Статическая HTML-платформа открывается автономно.
- HTTP-режим открывает платформу через Python backend.
- Backend health endpoint отвечает.
- Публичный `GET /api/health` не раскрывает абсолютный путь к SQLite; отдаёт только безопасные поля `scheme`, `storage`, `db_ready`, `time`.
- Backend отдает базовые security headers для API и HTML: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy`; в HTTPS-режиме добавляется HSTS.
- Backend ограничивает размер JSON POST-запросов; чрезмерный payload получает `413`, лимит можно настроить через `QH_MAX_JSON_BYTES`.
- Backend readiness endpoint доступен директору через `GET /api/readiness`.
- `/api/readiness` подтверждает локальную готовность SQLite/API-контура.
- `/api/readiness` отдельно проверяет целостность SQLite через `PRAGMA quick_check`; повреждённая база не проходит `local_ready`.
- `/api/readiness` отдельно показывает версию схемы SQLite; база без актуальной `schema_meta` не проходит `local_ready`.
- `/api/readiness` отдельно подтверждает обслуживание сессий; просроченные токены отзываются и не остаются активными.
- `GET /api/sessions` доступен только директору, показывает активные входы без token hash и отмечает текущую сессию.
- Директор может выполнить `POST /api/sessions/revoke-expired` и `POST /api/sessions/revoke-others`; текущая сессия директора остается рабочей.
- `GET /api/access/matrix` доступен директору и показывает матрицу ролей строительной компании: генеральный директор, главный инженер, прораб, бригадир, бухгалтер и юрист / разрешитель.
- `GET /api/access/matrix.docx` доступен директору и выгружает Word-матрицу доступа по ролям, объектам, действиям и ограничениям без демо-паролей и token hash.
- `/api/readiness` отдельно проверяет manifest резервных копий: наличие SHA-256, совпадение checksum и целостность `.sqlite3`; старые валидные manifest без checksum дополняются автоматически.
- `/api/readiness` отдельно проверяет свежесть последней резервной копии; порог задаётся через `QH_BACKUP_MAX_AGE_HOURS`, по умолчанию 24 часа.
- `/api/readiness` не раскрывается без токена и недоступен ролям без полного доступа.
- `/api/readiness` явно показывает `production_ready=false`, пока не подключены внешние production-зависимости.
- При `QH_REQUIRE_PRODUCTION=1` или `--require-production` сервер отказывается стартовать, пока все обязательные production-гейты не имеют статус `pass`.
- `--preflight` выводит readiness-паспорт без занятия HTTP-порта; вместе с `--require-production` возвращает код `2` при незакрытых production-гейтах.
- `--preflight-json` выводит тот же readiness-паспорт в машинно-читаемом JSON для CI/systemd/операторских проверок.
- `GET /api/acceptance/passport` доступен директору и показывает локальную приемку, production-приемку, backup-статус и production blockers в одном ответе.
- `GET /api/production/plan` доступен директору и показывает точный план подключения боевого контура: статус, ответственного, переменные/команды и следующий шаг по каждому production-гейту.
- `GET /api/production/evidence` доступен директору и показывает evidence-регистр по production-гейтам: статус доказательств, ответственный, дедлайн, заметка/ссылка на подтверждение и текущий статус gate.
- `POST /api/production/evidence` доступен директору и сохраняет evidence по выбранному production-gate в SQLite с audit-событием; статус `done` требует заполненное доказательство.
- `GET /api/production/evidence.docx` доступен директору и выгружает Word-реестр доказательств по production gate без демо-паролей, токенов и runtime-путей.
- `GET /api/production/request-pack` доступен директору и показывает пакет запросов по незакрытым production blockers: адресат, канал, тема, что запросить и какое доказательство вернуть.
- `GET /api/production/request-pack.docx` доступен директору и выгружает Word-пакет готовых запросов к Минстрою/ДГАСК, IT, DevOps, ЭЦП, платежному провайдеру, storage/backup и юристу.
- `GET /api/production/official-letters` доступен директору и формирует проекты официальных писем/заявок по текущим production blockers на основании request-pack.
- `GET /api/production/official-letters.docx` доступен директору и выгружает Word-комплект писем с адресатами, темами, текстами обращений, доказательствами и блоком подписи директора.
- `POST /api/production/request-pack/tracker` доступен директору и сохраняет трекер отправки по production gate: статус, исходящий номер, дата отправки/ответа, контакт, ответственный и заметка. Статус `sent` переводит evidence в `waiting_external`, `evidence_attached` - в `done`.
- `POST /api/external/sacc2-status/attach` доступен директору и фиксирует текущую публичную проверку sacc2 в gate `sacc2_api`: создает служебный номер `SACC2-STATUS-*`, обновляет request-pack/evidence и сохраняет audit/notification без паролей и API-ключей.
- `GET /api/production/action-board` доступен директору и группирует незакрытые production-действия по ролям: генеральный директор, DevOps, IT/интегратор, бухгалтер, юрист/разрешитель, Минстрой/ДГАСК и служба безопасности.
- `GET /api/production/action-board.docx` доступен директору и выгружает Word-карточки закрытия blockers по ролям.
- `GET /api/production/launch-sequence` доступен директору и показывает пошаговую карту запуска: управление, инфраструктура, интеграции, безопасность документов, backup и финальный go/no-go.
- `GET /api/production/launch-sequence.docx` доступен директору и выгружает Word-план с текущим следующим шагом, зависимостями, ответственными и доказательствами.
- `GET /api/production/remaining-work` доступен директору и показывает отдельный отчет “что осталось”: процент готовности, ближайший шаг, список открытых production-шагов, ответственных и нужные доказательства.
- В отчете “что осталось” директор может назначить ответственного, дедлайн, статус и заметку/доказательство по открытому production gate; изменения сохраняются в evidence-регистр и сразу возвращаются в карточки запуска.
- `GET /api/production/remaining-work.docx` доступен директору и выгружает Word-отчет “что осталось до боевого запуска” без демо-паролей и token hash.
- `GET /api/production/top-actions` и `GET /api/production/top-actions.docx` доступны директору и выгружают короткий список ближайших действий с метками срочности, сроками, ответственными и действиями.
- `GET /api/production/alerts` и `POST /api/production/alerts/generate` доступны директору: просроченные, сегодняшние, ближайшие, заблокированные и первые шаги без дедлайна превращаются в отдельный список предупреждений и общий журнал уведомлений без дублей.
- `GET /api/production/qa-evidence` и `.docx` доступны директору и выгружают QA-пакет: рабочая ссылка, live evidence, команды regression/browser/responsive/accessibility/live-smoke/release/go-no-go и список актуальных артефактов.
- `GET /api/production/status-board` и `.docx` доступны директору и показывают единый статус запуска: рабочая ссылка, локальная/production готовность, сколько осталось, ближайшие действия, полный список открытых шагов, QA-команды и артефакты.
- `GET /api/calendar` доступен после входа и собирает единый календарь сроков из поручений, запросов ДГАСК/Минстроя, документов, проверок, платежей и штрафов с учетом ролевого доступа к объектам.
- `GET /api/chat` и `POST /api/chat` доступны после входа: внутренний чат сохраняет сообщения в SQLite, а локальный ИИ-помощник отвечает по текущим срокам, запросам ДГАСК, штрафам, платежам и открытым действиям без внешнего API-ключа.
- `GET /api/production/future-roadmap` доступен директору и фиксирует будущий контур: мобильная field-версия для прораба/бригадира с фотофиксацией, offline queue, объектным доступом и связкой с `/api/tasks`, `/api/documents`, `/api/chat`, `/api/calendar`.
- В том же roadmap зафиксирован платежный слой Кыргызстана: provider registry по актуальным реестрам НБКР, Элкарт/банк-эквайринг, QR/deeplink, callback/reconciliation и запрет списания без явного подтверждения бухгалтера или директора.
- `ops/collect_acceptance_evidence.py` сохраняет sanitized JSON-доказательство приемки в `outputs/acceptance-evidence-current.json`: release acceptance, live smoke, backup restore drill, redacted-команды и `failed_stages` без паролей и token hash.
- `GET /api/acceptance/evidence` и `/api/acceptance/evidence.json` доступны директору и показывают последний очищенный acceptance evidence JSON прямо в платформе: `ok`, `failed_stages`, этапы, команды без секретов и артефакты.
- `ops/completion_audit.py` создает `outputs/completion-audit-current.json`: requirement-by-requirement аудит с `local_handoff_ready`, `production_ready`, доказанными стадиями и внешними blockers.
- `GET /api/acceptance/completion-audit` и `/api/acceptance/completion-audit.json` доступны директору и показывают completion audit в интерфейсе: local handoff, production статус, доказанные проверки и что осталось.
- `GET /api/production/plan.docx` доступен директору и выгружает Word-план подключения; контрольный DOCX отрендерен и визуально проверен.
- `GET /api/production/env.example` доступен директору и выгружает безопасный шаблон production-переменных без демо-паролей и runtime-токенов.
- `POST /api/production/env/validate` доступен директору и проверяет вставленный production `.env` без сохранения и без возврата секретных значений.
- `POST /api/production/auth-cutover/validate` доступен директору и проверяет bootstrap-администратора, роль, парольную политику и `QH_DISABLE_DEMO_USERS=1` без сохранения и без возврата пароля.
- `POST /api/production/hooks/validate` доступен директору и проверяет готовность hook-команд из `.env` к dry-run JSON smoke: `QH_REQUIRE_HOOK_JSON=1`, наличие команд и обязательные маркеры `{payload}`, `{file}`, `{backup}`, `{manifest}`.
- `POST /api/production/sacc2/validate` доступен директору и проверяет готовность sacc2 / ДГАСК контура: HTTPS API URL, API-ключ, sync-команду, JSON-hook статус и `QH_SACC2_STATUS_MAP` для внутренних статусов `needs_company`, `informed`, `review`, `done`.
- `POST /api/production/eds/validate` доступен директору и проверяет готовность ЭЦП-контура: провайдера, HTTPS API URL, команду подписи, маркер `{payload}` и JSON-hook режим без возврата команды подписи.
- `POST /api/production/payments/validate` доступен директору и проверяет готовность платежного контура для госпошлин и штрафов: HTTPS gateway URL, команду подтверждения оплаты, маркер `{payload}` и JSON-hook режим без возврата команды.
- `POST /api/production/storage/validate` доступен директору и проверяет production-хранилище документов: внешний режим, URL, sync-команду, маркер `{file}` и JSON-hook режим без возврата команды.
- `POST /api/production/av/validate` доступен директору и проверяет AV-сканер: команду с маркером `{file}`, JSON-hook режим и обязательное поведение проверки файла до сохранения.
- `POST /api/production/backups/schedule/validate` доступен директору и проверяет расписание SQLite-бэкапов, `QH_BACKUP_ON_START=1` и порог свежести копий.
- `POST /api/production/backups/remote/validate` доступен директору и проверяет удаленное хранение бэкапов: URL, команду, маркеры `{backup}`/`{manifest}` и JSON-hook режим без возврата команды.
- `POST /api/production/cutover/validate` доступен директору и объединяет домен/HTTPS, `.env`, учетные записи, hooks, sacc2, ЭЦП, платежи, хранилище, AV, бэкапы и юридический каталог в один go/no-go отчет без возврата секретов и shell-команд.
- `POST /api/production/cutover.docx` доступен директору и выгружает Word-отчет production cutover по тем же входным данным без раскрытия секретов и shell-команд.
- `GET /api/production/checklist` доступен директору и показывает stages/commands для preflight, live smoke, go/no-go и final acceptance.
- `GET /api/production/checklist.docx` доступен директору и выгружает Word-чеклист production-запуска.
- `production_env_values` блокирует запуск при placeholder-значениях в production-переменных, включая `CHANGE_ME`, `example.test`, `provider.example`, `YYYY-MM-DD` и короткие API-ключи.
- Production-гейты внешних hook-команд проверяют, что первый executable существует и доступен для запуска, а не только что переменная окружения заполнена.
- Подготовлен production runbook, systemd unit с `ExecStartPre` preflight, nginx reverse proxy пример и серверный smoke-check по URL.
- Подготовлен release-package сборщик: архив включает только backend/static/ops/docs и исключает SQLite, uploads, backups, outputs, кеши и скриншоты.
- Подготовлен release acceptance-check: архив сверяется с `RELEASE_MANIFEST.json` по SHA-256, распаковывается во временную папку, Python-файлы компилируются, preflight проходит из распакованной копии.
- Подготовлен deployment audit: release acceptance проверяет deployment-комплект, а реальный `/etc/qurulush-hub/company-platform.env` можно строго проверить на placeholder-значения, production-флаги и права доступа.

- Подготовлен `ops/hook_contract_smoke.py`: по закрытому env он запускает реальные hook-команды на dry-run payload и проверяет JSON-ответы до production-приемки.
- Подготовлен `ops/render_deployment_files.py`: по реальному домену генерирует готовые systemd/nginx/go-no-go файлы без ручной замены `company.example`.
- При заданных `QH_SACC2_API_URL`, `QH_SACC2_API_KEY` и `QH_SACC2_SYNC_CMD` сервер отправляет очищенный пакет обмена через `POST /api/sacc2/sync`; API-ключ не попадает в payload.

- Readiness показывает отдельную проверку `Боевой администратор`.
- HTTP-интерфейс начинается с экрана входа по email и паролю.
- После входа интерфейс показывает текущего пользователя и открывает данные его роли.
- Logout в интерфейсе отзывает серверную сессию и возвращает пользователя на экран входа.
- Пользователи хранятся отдельно в SQLite-таблице `users`.
- Пароли проверяются через PBKDF2-хеш и не лежат в payload состояния.
- Сессии хранятся в SQLite-таблице `sessions`.
- Bearer-токен не хранится в базе в открытом виде, используется SHA-256 хеш.
- Токен сессии имеет срок действия.
- Logout инвалидирует токен.
- Смена пароля проверяет текущий пароль, сохраняет новый PBKDF2-хеш и отзывает остальные сессии пользователя.
- После 5 неверных попыток входа в пределах 15 минут сервер временно блокирует вход и возвращает `429`.
- Успешный вход очищает счётчик неверных попыток.
- Сервер не отдаёт список пользователей в `/api/state`.
- `/api/state` фильтрует видимость разделов по роли пользователя.
- `/api/state` фильтрует объекты и связанные записи по назначенным объектам сотрудника.
- `/api/state` фильтрует поручения по роли и назначенным объектам.

- При заданном интервале `QH_BACKUP_INTERVAL_MINUTES`, `QH_BACKUP_INTERVAL_SECONDS` или `QH_BACKUP_SCHEDULE` сервер автоматически создаёт SQLite-бэкапы с JSON-manifest.
- При заданном `QH_BACKUP_REMOTE_CMD` сервер выгружает `.sqlite3` и `.json` manifest через внешнюю команду; успешная выгрузка отмечается `remote_synced_at`.
- При заданном `QH_PAYMENT_GATEWAY_CMD` сервер подтверждает оплату через внешний шлюз до сохранения статуса `Оплачено`.
- UI-действия через HTTP подтверждены последующей API-проверкой состояния.
- Автономный `localStorage` режим не сломан.

## Что ещё нужно для промышленной эксплуатации

- Заменить демо-аккаунты на полноценную корпоративную авторизацию.
- Для первого рабочего запуска задать bootstrap-админа и включить `QH_DISABLE_DEMO_USERS=1`.
- Заполнить `.env.production.example`, проверить его через раздел `Готовность запуска`, сохранить боевой `.env.production` на сервере и пройти `--preflight --require-production`.
- Собрать чистый release zip через `ops/build_release_package.py` и переносить на VPS именно его, а не рабочую папку с runtime-данными.
- Перед переносом проверить release zip через `ops/release_acceptance_check.py`.
- Настроить systemd/nginx по `ops/README_PRODUCTION.md` и пройти `ops/production_smoke_check.py --require-production`; smoke-check должен подтвердить локальные gates `sqlite_integrity`, `schema_version`, `session_maintenance`, `backup_manifests`, `backup_freshness`, директорский контроль сессий, публичный статус sacc2, фиксацию sacc2 в request-pack/evidence, dry-run проверку последнего backup и `acceptance passport production=True`.
- Выполнить `ops/backup_restore_drill.py` на production backup-каталоге: последняя копия должна восстановиться во временную SQLite, пройти `PRAGMA quick_check`, сверить счетчики и удалить временную базу.
- Выполнить `ops/go_no_go_check.py --deployment-root ... --env ... --require-production-config --hook-contract-smoke --require-production`: итоговый JSON должен вернуть `ok=true`, пустой `failed_stages` и успешные стадии release acceptance, deployment audit, hook contract smoke, live smoke-check и backup restore drill.
- Выполнить `ops/completion_audit.py` после финального evidence: для локальной передачи должно быть `local_handoff_ready=true`, а для боевого запуска дополнительно `production_ready=true`.
- Выпустить и подключить доверенный production-сертификат для домена.
- Настроить реальный production AV-сканер, карантин, политику хранения оригиналов и внешнее объектное хранилище.
- Настроить реального провайдера ЭЦП и production-команду `QH_EDS_SIGN_CMD`.
- Настроить реальный платёжный шлюз и production-команду `QH_PAYMENT_GATEWAY_CMD`.
- Получить официальный доступ ДГАСК / sacc2, регламент статусов и настроить production-команду `QH_SACC2_SYNC_CMD`.
- Сверить справочник требований с действующими НПА, тарифами, формами, сроками и официальными регламентами Минстроя / ДГАСК КР.
- Настроить production-команду внешнего хранения бэкапов и мониторинг успешной выгрузки.
- Провести пользовательскую приемку с реальными сотрудниками компании.
